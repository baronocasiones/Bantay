# Bantay

**The safety net that never phones home.**

Bantay watches for falls on a mid-range Android phone and alerts an emergency
contact by SMS. It runs entirely on-device: the detection, the wording, the
outbox queue when the signal drops. Nothing in the alert path makes a network
request.

Built for the AppBuildersPH Hackathon 2026, Local AI track. Target user is a
senior living alone in a rural barangay: intermittent cell signal, a family
member an hour away, and a golden hour that only counts if somebody is told.

Not a medical device. No diagnostic claim.

## Why local is not a preference

Continuous accelerometer streaming to a cloud API is financially unshippable
per user, and an alert that arrives 1.5 seconds late is a failed alert, not a
slow one. Motion data is health data, so under the Data Privacy Act streaming
it is a legal liability. And when you actually need it, the cloud does not
exist. So Bantay never calls it.

## Two paths, separated on purpose

Bantay splits fall handling into two independent paths.

| | Path 1 (safety-critical) | Path 2 (optional) |
|---|---|---|
| **What** | Native fall detection, countdown, haptics, SMS, optional emergency location, local incident history | On-device LLM proposes alert wording |
| **Depends on** | Nothing | Qwen3-0.6B via LiteRT-LM |
| **Budget** | Under 100 ms to alarm | 40 tokens, 2 s wall-clock |
| **On failure** | n/a | Hardcoded bilingual template, unedited |

Path 1 is the product. A confirmed fall starts its fixed 15-second countdown
and SMS flow. GPS lookup is optional and time-bounded; without a usable fix,
the message says `Location unavailable`. Manual SOS does not wait for GPS.
Incident records and their actual SMS/countdown outcomes stay in an app-private
SQLite database, with local search, filters, and detail views.

Path 2 can propose shorter wording while the countdown runs. Native Path 1 keeps
its fixed message ready and accepts a model candidate only when it arrives
before the existing deadline and passes validation. Model failure or a late
candidate never delays SMS.

The rule that governs every change here: **a life-saving path should never
wait on a generative model.**

## The model

Path 2 runs Qwen3-0.6B, `dynamic` quantization, from the LiteRT-LM community.
It is **not** kept in source control (329 MiB, and GitHub rejects files over
100 MiB); it ships as a release attachment:

- Release:
  [`model-qwen3-0.6b-wi4b32-v1`](https://github.com/baronocasiones/Bantay/releases/tag/model-qwen3-0.6b-wi4b32-v1)
- Asset:
  [`Qwen3-0.6B_dynamic_wi4b32_afp32.litertlm`](https://github.com/baronocasiones/Bantay/releases/download/model-qwen3-0.6b-wi4b32-v1/Qwen3-0.6B_dynamic_wi4b32_afp32.litertlm),
  344,671,744 bytes
- md5 `0c63f12e688bc91d1bd4577c9858d262`
- sha256 `03e7da1eb1108b50dffaa9bb52cc7bcbad2eb0c66ca990267f480c1e545d2856`
- Upstream: [litert-community/Qwen3-0.6B](https://huggingface.co/litert-community/Qwen3-0.6B)

Do **not** substitute `qwen3_0_6b_mixed_int4.litertlm` from the same
publisher. That file is broken: it ignores its input and answers every prompt
with the same generic greeting, on the demo phone and under Google's LiteRT-LM
CLI alike. A truncated download fails in exactly the same way, so checksum the
copy you sideload, on the device, after installing:

```sh
MODEL=Qwen3-0.6B_dynamic_wi4b32_afp32.litertlm
md5sum $MODEL                                     # host
adb push $MODEL /data/local/tmp/$MODEL
adb shell run-as ph.appbuilders.bantay_app cp /data/local/tmp/$MODEL app_flutter/$MODEL
adb shell run-as ph.appbuilders.bantay_app md5sum app_flutter/$MODEL  # must match
```

The `_xnnpack_cache` files that appear next to the model are regenerated by
the runtime on first run and mean nothing to copy elsewhere.

## Build

This workstation does not put Flutter or the Android SDK on `PATH`:

```sh
export ANDROID_HOME=/home/adrian/codes/appbuilder-stufff/.android-sdk
export ANDROID_SDK_ROOT="$ANDROID_HOME"
FLUTTER=/home/adrian/flutter/bin/flutter
```

Harness, for the demo phone (Samsung SM-A127F, Android 13, arm64, Exynos 850):

```sh
cd bantay_app
$FLUTTER build apk --debug --target-platform android-arm64 \
  --dart-define=BANTAY_MODEL_PATH=/data/user/0/ph.appbuilders.bantay_app/app_flutter/Qwen3-0.6B_dynamic_wi4b32_afp32.litertlm \
  --dart-define=BANTAY_BACKEND=gpu
$ANDROID_HOME/platform-tools/adb install -r build/app/outputs/flutter-apk/app-debug.apk
$ANDROID_HOME/platform-tools/adb shell am start -n ph.appbuilders.bantay_app/.MainActivity
```

Always pass `--target-platform android-arm64`. Without it the build bundles
32-bit and x86_64 plugin libraries that cannot run on the target.

Checks:

```sh
cd bantay_llm  && $FLUTTER test && $FLUTTER analyze
cd bantay_app  && $FLUTTER test && $FLUTTER analyze
```

## Status

Implemented in the current source:

- Native impact cascade and fixed countdown, with manual SOS and SMS outcomes
  recorded in the local incident history.
- Optional emergency coordinates: a fresh fix is requested during a fall
  countdown; SOS uses only a sufficiently recent last-known fix. Neither path
  waits indefinitely for location.
- Local movement baseline refines the movement label attached to an event. It
  does not change the fall trigger or impact, rotation, and stillness gates.
- History and incident details show real saved records and SMS/countdown
  outcomes. No demo incidents are seeded, and no cloud sync is used.
- The optional local model runs alongside the native countdown. Kotlin checks
  the incident identity and deadline before using generated wording; the
  fallback text remains available.

Previously verified on the demo phone:

- Accelerometer pipeline end to end: 41-50 Hz measured, 19-20 Hz cadence,
  65 s screen-off with sampling intact, cold attach re-draining with honest
  dropped counts. These measurements predate the current 5.0 g impact gate.
- Path 2: the documented model loads and generates on the phone on both CPU
  and GPU backends; the GPU OpenCL accelerator cuts prefill 2.6x.
- Path 2's 2-second budget is **not** reachable on this hardware. Prefill
  costs about 1.3 s per prompt token on an Exynos 850, which is why the
  production path correctly selects the bilingual template. `llmUsed` is
  false, the SMS text is complete, and the alert never waits.

The new detector, GPS, SMS, model-coordination, and history flows still need
fresh end-to-end device verification. Earlier carpet-drop measurements used a
3.5 g impact gate and do not validate the current 5.0 g threshold. See
`docs/path1-module.md` and `docs/ui-flow.md` for implementation details and the
current device checklist.

Passing `flutter test` is not evidence the model loads or generates on the
phone. Device claims here come from `screencap` and logcat, not from the test
suite.

## Hard rules

- The alert path never waits on the model. `BantayPath2` never throws,
  `prepareFromFile` returns `false` on failure, and `compose` returns the
  template on any model failure, timeout, or fact-check rejection.
- `alert_composer.dart` owns the prompt, the template, and the fact checker.
  Edit them together; the checker is what catches a prompt regression.
- `maxTokens` (2048) is the KV cache on `getActiveModel`; `maxOutputTokens: 40`
  caps generation on `createSession`. Conflating them is a package trap.
- Model files stay out of source control. Sideload and checksum instead.
